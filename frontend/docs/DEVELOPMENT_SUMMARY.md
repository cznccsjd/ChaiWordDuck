## 📖 项目概述

### 项目背景
**拆词鸭 (ChaiWord Duck)** 是一款专注于成人英语长单词学习的创新教育产品。通过独特的"语言游戏"方法（基于维特根斯坦哲学），让用户真正理解并记住那些看起来复杂的长单词。

### 核心价值主张
- 不是给单词下定义，而是教你如何使用
- 不是机械重复，而是理解语境
- 不是孤立记忆，而是建立连接

### 目标用户
1. 考试备考群体（大学生、考研、托福/雅思）
2. 职场人士（阅读英文文献、商务邮件）
3. 终身学习者（有英语基础，想攻克长单词）

## 🎯 关键技术决策

### 1. 前端技术栈

#### Next.js 14 (App Router)
**选择理由**：
- 服务端渲染（SEO优化）
- 文件路由系统（开发效率高）
- 内置图片优化
- 强大的社区支持

**风险与对策**：
- 风险：App Router相对新，部分第三方库兼容性问题
- 对策：使用成熟的库（Zustand、Axios），避免过度依赖实验性功能

#### TypeScript
**选择理由**：
- 类型安全，减少运行时错误
- 更好的IDE支持（自动补全、重构）
- 便于团队协作和维护

**实施标准**：
- 禁止使用any类型
- 所有函数必须有类型注解
- 使用Zod进行运行时验证

#### Tailwind CSS
**选择理由**：
- 快速开发，无需命名CSS类
- 内置响应式设计工具
- 可定制的设计系统（色彩、间距）

**实施标准**：
- 使用设计token（colors、spacing）
- 组件化复用（避免重复样式）
- 遵循Mobile First原则

### 2. 后端技术栈（待实施）

#### FastAPI
**选择理由**：
- 高性能（基于ASGI）
- 自动生成OpenAPI文档
- 强大的类型验证（Pydantic）
- 异步支持

#### PostgreSQL
**选择理由**：
- 关系型数据库，ACID保证
- 丰富的数据类型（JSON、Array）
- 强大的查询优化器
- 适合复杂查询（收藏、查询历史）

#### Redis
**选择理由**：
- 高性能缓存（单词查询结果）
- 查询次数计数（原子操作）
- TTL过期机制（自动清理）

## 🚨 风险和挑战

### 技术风险

#### 1. OpenAI API依赖
**风险描述**：
- API调用成本高（每次查询约$0.002）
- API可能不稳定或限流
- 生成质量不稳定

**应对策略**：
- 使用Redis缓存已生成的单词手册（永久缓存）
- 预生成"黄金手册"（20-50个高频长单词）
- 设置API超时和重试机制
- 监控API成本，设置预算告警

#### 2. 查询次数限制实施
**风险描述**：
- 游客绕过限制（清除Cookie、切换IP）
- 限制过严影响用户体验

**应对策略**：
- 多维度识别（Cookie + localStorage + IP）
- 已查询单词不计次数（允许重复查看）
- 提供清晰的限制说明和注册引导

#### 3. 前后端联调问题
**风险描述**：
- API接口定义不一致
- 错误处理不统一
- 认证流程复杂

**应对策略**：
- 严格遵循架构文档的API定义
- 使用OpenAPI文档作为契约
- 编写API集成测试（覆盖所有端点）

### 业务风险

#### 1. 单词手册质量
**风险描述**：
- AI生成的内容可能不准确
- 记忆技巧可能不够创意

**应对策略**：
- 人工审核"黄金手册"（高频单词）
- 收集用户反馈，持续优化Prompt
- 引入专家评审机制

#### 2. 用户留存和活跃度
**风险描述**：
- 工具型产品，用完即走
- 复习功能缺失，用户遗忘

**应对策略**：
- MVP阶段先验证核心价值（单词手册质量）
- 后续迭代：智能复习系统、游戏化机制
- 社区功能：用户分享记忆技巧

## 🤝 团队协作情况

### 开发模式
**文档驱动开发 (DDD)**：
- 所有开发活动以.md文档为准
- 代码变更必须同步更新文档
- 文档与实际功能保持100%一致

**测试驱动开发 (TDD)**：
- 先写测试，再写实现
- 单元测试覆盖率≥95%
- API集成测试覆盖率≥90%

### Git版本控制
**Git Flow模型**：
- `main`：稳定发布版本
- `develop`：开发主分支
- `feature/*`：功能开发分支（如`feature/frontend-ui`）
- `bugfix/*`：Bug修复分支
- `hotfix/*`：紧急修复分支

**Commit规范**：
- 遵循Conventional Commits规范
- 格式：`<type>(<scope>): <subject>`
- 示例：`feat(frontend): implement word detail page`

### 角色分工
- **产品经理**：需求分析、PRD编写
- **设计师**：UI设计、设计规范
- **架构师**：技术选型、架构设计
- **前端开发专家**：前端实现（已完成）
- **后端开发专家**：后端API开发（待开始）
- **测试专家**：测试设计、质量保证
- **调试专家**：Bug修复
- **项目助理**：文档管理、Git管理
